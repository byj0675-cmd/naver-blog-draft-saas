# Blogmate AI 소상공인 온보딩 설계안

## 1. 제품 방향

Blogmate AI의 온보딩은 일반적인 회원가입 폼이 아니라 **업체의 콘텐츠 담당자가 되는 첫 인터뷰**여야 합니다. 고객은 프롬프트를 배우거나 마케팅 용어를 이해할 필요가 없습니다. 대신 본인의 영업 방식, 서비스, 고객 질문, 현장 사례를 편한 말로 입력하면 서비스가 이를 초안 작성 기준으로 정리합니다.

랜딩페이지의 약속은 “퇴근 후에도 블로그 숙제를 직접 하지 않아도 된다”는 해방감입니다. 따라서 온보딩에서도 처음부터 많은 입력을 요구하기보다, 빠르게 첫 결과를 확인하게 하고 이후 자료를 추가할수록 품질이 높아지는 구조를 사용해야 합니다.

> 핵심 경험: 업체 소개 3분 입력 → 첫 글감 선택 → 제목 3개와 초안 확인 → 부족한 정보만 추가 보완

## 2. 랜딩에서 온보딩으로 이어지는 전환 구조

랜딩페이지의 소구점과 버튼 문구는 온보딩의 첫 화면과 같은 언어를 사용해야 합니다.

| 랜딩 소구점 | CTA 문구 | 온보딩 첫 화면에서의 약속 |
|---|---|---|
| “오늘도 블로그 써야 한다고 생각만 하다 하루가 끝났나요?” | 내 업체 글쓰기 기준 만들기 | “사장님이 직접 프롬프트를 만들 필요 없이, 업체 정보를 먼저 정리합니다.” |
| “사장님의 시간은 글쓰기보다 본업에 쓰여야 합니다.” | 3분 만에 업체 등록하기 | “모든 칸을 한 번에 채우지 않아도 됩니다. 아는 것부터 저장하세요.” |
| “키워드·글감·사진 고민을 줄여드립니다.” | 첫 글 초안 만들어보기 | “업체 정보를 바탕으로 첫 제목 후보와 글 구조를 준비합니다.” |
| “내 매장다운 글을 꾸준히 쌓아보세요.” | 무료로 시작하기 | “첫 글을 만든 뒤 필요한 정보만 추가해 품질을 높일 수 있습니다.” |

로그인 이후에는 빈 대시보드로 보내기보다, 브랜드가 없는 사용자에게 `업체 등록 시작` 화면을 우선 노출합니다. 사용자가 랜딩에서 `필라테스`, `미용실`, `누수·철거` 같은 업종 예시를 보고 들어왔다면 해당 업종을 선택값으로 미리 채우되, 실제 업체 정보는 사용자가 직접 확인해야 합니다.

## 3. 전체 온보딩 여정

온보딩은 6단계로 구성하되, 각 단계마다 저장과 건너뛰기를 지원합니다. 처음부터 모든 정보를 입력하지 않아도 첫 초안을 만들 수 있어야 합니다.

| 단계 | 화면명 | 고객이 입력하는 것 | 완료 기준 |
|---:|---|---|---|
| 1 | 업체 기본 정보 | 상호, 업종, 지역, 연락처, 홈페이지, 영업시간 | 상호와 업종 입력 |
| 2 | 무엇을 판매하나요 | 서비스·상품 여러 개, 가격, 소요 시간, 대상 고객 | 대표 서비스 1개 이상 |
| 3 | 우리 업체만의 전문성 | 잘하는 일, 작업·수업 과정, 차별점, 주의사항 | 자유 설명 1개 이상 또는 건너뛰기 |
| 4 | 고객 질문과 실제 답변 | FAQ, 상담 시 자주 설명하는 내용 | 질문·답변 1개 이상 또는 건너뛰기 |
| 5 | 글쓰기 기준 | 핵심·보조 키워드, 금지 표현, 원하는 말투, CTA | 핵심 키워드 1개 이상 |
| 6 | 참고 자료와 첫 글 | 기존 글 URL, 홈페이지 URL, 사진, 첫 글 주제 | 첫 글 주제 선택 |

화면 상단에는 `업체 등록 40%` 같은 진행률보다 “첫 글을 만들기까지 3단계 남음”처럼 결과 중심 문구를 표시합니다. 각 단계의 오른쪽에는 “나중에 입력”을 제공하고, 저장 시점에는 “현재까지의 정보로도 기본 초안을 만들 수 있습니다”라고 안내합니다.

## 4. 화면 레이아웃

### 4.1 공통 데스크톱 레이아웃

왼쪽에는 220~250px 너비의 단계 목록을 배치하고, 오른쪽에는 입력 카드와 예시·도움말을 배치합니다. 대시보드의 기존 업무 도구 톤을 유지하되, 온보딩에서는 빈 화면의 부담을 줄이기 위해 질문형 제목을 사용합니다.

```text
┌────────────────────────────────────────────────────────────┐
│ blogmate                         저장됨 · 2단계 / 6단계     │
├───────────────┬────────────────────────────────────────────┤
│ 업체 등록      │ 무엇을 판매하나요?                         │
│ ✓ 기본 정보    │ 고객에게 실제로 제공하는 서비스를 적어주세요. │
│ 2 상품·서비스  │                                            │
│ 3 전문성       │ [대표 서비스 카드                         ] │
│ 4 고객 질문    │ [서비스명] [가격] [소요 시간]               │
│ 5 글쓰기 기준  │ [이 서비스가 필요한 고객은 누구인가요?]    │
│ 6 첫 글        │ + 다른 서비스 추가                         │
│               │                                            │
│               │ 예시: 필라테스 리포머 10회권                  │
│               │                                            │
│               │ [이전]                         [저장 후 계속] │
└───────────────┴────────────────────────────────────────────┘
```

입력 카드 안에는 업종별 예시를 보여주되 예시 데이터를 실제 저장값으로 사용하지 않습니다. 사용자가 필라테스를 선택하면 “개인레슨, 그룹레슨, 체형교정, 산전·산후 프로그램”을 예시로 보여주고, 미용실이면 “커트, 염색, 펌, 클리닉”을 보여줍니다. 누수·철거업체라면 “누수 탐지, 부분 철거, 원상복구, 폐기물 처리”를 보여줍니다.

### 4.2 모바일 레이아웃

모바일에서는 왼쪽 단계 목록을 상단의 가로 진행 표시로 바꾸고, 한 화면에 질문 하나 또는 카드 하나만 보여줍니다. 입력 중 이탈을 줄이기 위해 상단에 저장 상태를 표시하고, 하단에는 고정된 `이전`·`계속` 버튼을 둡니다.

```text
┌──────────────────────┐
│ ← 업체 등록     저장됨 │
│ ●──●──○──○──○──○      │
│ 2 / 6                 │
│                      │
│ 무엇을 판매하나요?     │
│ 서비스 하나를 등록하면  │
│ 글의 주제가 더 정확해져요│
│                      │
│ [서비스명            ] │
│ [가격                ] │
│ [소요 시간           ] │
│ [고객에게 어떤 도움?  ] │
│                      │
│ + 다른 서비스 추가      │
│                      │
│ [이전]       [계속]    │
└──────────────────────┘
```

긴 자유 입력은 자동 높이 조절 textarea를 사용하고, 입력값이 사라지지 않도록 단계 이동 전에 자동 저장합니다. 모바일 키보드가 열렸을 때 하단 고정 버튼이 입력창을 가리지 않도록 충분한 하단 여백을 둡니다.

## 5. 단계별 상세 설계

### 5.1 1단계: 업체 기본 정보

첫 화면은 사업자등록증 같은 딱딱한 양식이 아니라 “고객이 업체를 찾을 때 가장 먼저 궁금해하는 정보”라는 설명으로 시작합니다. 상호와 업종만 필수로 두고, 주소·전화번호·홈페이지·영업시간은 선택 입력으로 둡니다.

필라테스 업체라면 지역과 지점을 분리해 “성수점”, “강남점”처럼 브랜드별 운영 단위를 구분할 수 있어야 합니다. 이후 브랜드당 월 12건 제한을 적용하므로 지점이 서로 다른 브랜드인지 같은 브랜드의 지점인지 선택하게 하는 것이 필요합니다.

### 5.2 2단계: 상품·서비스 카드

업체의 상품과 서비스를 하나의 긴 문장으로 입력하게 하지 않고 반복 가능한 카드로 저장합니다. 카드에는 `서비스명`, `가격 또는 견적 기준`, `소요 시간`, `대상 고객`, `포함 내용`, `예약·문의 방법`, `주의사항`을 둡니다.

미용실의 “셋팅펌”과 “남성 커트”처럼 상품마다 가격과 시간이 다르기 때문에 이 구조가 사실성에 가장 중요합니다. 누수·철거업체는 고정 가격이 없을 수 있으므로 가격 대신 “현장 확인 후 견적”, “평수·작업 범위에 따라 변동” 같은 견적 기준을 입력할 수 있어야 합니다.

### 5.3 3단계: 전문 분야와 작업 방식

이 단계는 AI가 일반적인 인터넷 글과 업체의 실제 노하우를 구분하게 하는 핵심입니다. 질문은 다음처럼 구체적으로 제시합니다.

| 질문 | 입력 예시 |
|---|---|
| 어떤 일을 가장 잘하나요? | 허리 통증이 있는 초보 회원의 기초 체형 교정 |
| 작업·수업은 어떤 순서로 진행되나요? | 상담 → 움직임 평가 → 개인별 기구 설정 → 마무리 피드백 |
| 고객이 다른 업체와 비교해 선택하는 이유는 무엇인가요? | 원장 직접 상담, 소규모 수업, 수업 후 운동 기록 제공 |
| 반드시 안내해야 할 주의사항은 무엇인가요? | 통증이 심한 경우 의료기관 상담을 먼저 권장 |
| 절대 쓰면 안 되는 표현은 무엇인가요? | 완치, 100% 효과, 무조건 최저가 |

자유 입력이 부담스러운 사용자를 위해 질문별 짧은 예시와 음성 입력 또는 메모 붙여넣기를 고려할 수 있습니다. 단, 음성 기능은 후속 기능이며 MVP에서는 textarea로 시작합니다.

### 5.4 4단계: FAQ와 실제 상담 답변

FAQ는 초안에 반복적으로 유용한 정보가 되는 영역입니다. 질문과 답변을 한 쌍으로 추가하고, “공개해도 되는 답변인가요?” 토글을 둡니다. 내부 운영 메모와 고객 공개 답변을 분리하면 가격 협상 기준이나 내부 메모가 그대로 글에 노출되는 문제를 줄일 수 있습니다.

### 5.5 5단계: 키워드와 글쓰기 기준

핵심 키워드와 보조 키워드는 태그 형태로 입력하고, 키워드마다 “주요 지역”, “서비스명”, “문제·고민”, “대상 고객” 분류를 지정합니다. 사용자는 SEO 용어를 몰라도 되도록 “고객이 검색창에 입력할 만한 말”이라는 설명을 사용합니다.

금지 표현은 반드시 별도 영역으로 두고, `근거 없는 최상급`, `의료적 효능 단정`, `경쟁 업체 비방`, `확인되지 않은 가격`을 기본 안내로 표시합니다. 말투는 기존 글 URL 분석으로 자동 제안하되, 사용자가 “차분한 존댓말”, “친근하지만 과장하지 않는 말투”처럼 수정할 수 있게 합니다.

### 5.6 6단계: 참고 자료와 첫 글 만들기

공식 홈페이지·메뉴판·가격표·공지·기존 네이버 글 URL을 추가할 수 있습니다. 이후 “이번 주에 어떤 글이 필요하세요?”라는 질문으로 첫 글 주제와 검색 키워드를 선택합니다. 이 단계에서 `저장된 업체 정보만 사용`, `공식 링크만 확인`, `최신 공개 자료도 검색`의 세 가지 모드를 제공합니다.

## 6. 데이터 구조

### 6.1 MVP 권장 구조

현재 프로젝트는 `brandProfiles.briefJson`으로 브리프를 저장하고 있으므로, 첫 구현에서는 기존 컬럼을 유지하면서 JSON 구조를 확장할 수 있습니다. 다만 서비스·FAQ·출처가 반복적으로 늘어나면 하나의 JSON 문자열이 지나치게 커지므로, 다음 단계에서 정규화 테이블로 분리합니다.

```ts
type BusinessBrief = {
  summary: string;
  location: { city?: string; district?: string; address?: string; branchName?: string };
  contact: { phone?: string; website?: string; hours?: string; closedDays?: string };
  services: ServiceItem[];
  expertise: KnowledgeNote[];
  faqs: FaqItem[];
  keywords: { primary: string[]; secondary: string[]; forbidden: string[] };
  writingGuide: { tone?: string; preferredPhrases: string[]; forbiddenClaims: string[]; callToAction?: string };
  verifiedFacts: FactItem[];
  sourceLinks: SourceLink[];
};

type ServiceItem = {
  id: string;
  name: string;
  priceText?: string;
  durationText?: string;
  audience?: string;
  included?: string;
  bookingGuide?: string;
  cautions?: string;
};

type KnowledgeNote = {
  id: string;
  title: string;
  content: string;
  category: "process" | "expertise" | "case" | "caution" | "other";
  publishable: boolean;
};

type FaqItem = {
  id: string;
  question: string;
  answer: string;
  publishable: boolean;
};

type FactItem = {
  id: string;
  statement: string;
  sourceType: "owner" | "official_url" | "uploaded_file";
  sourceId?: string;
  verifiedAt?: string;
  status: "unverified" | "verified" | "needs_review";
};

type SourceLink = {
  id: string;
  url: string;
  title?: string;
  sourceType: "official_site" | "naver_blog" | "government" | "manufacturer" | "other";
  checkedAt?: string;
  allowedForDraft: boolean;
};
```

### 6.2 후속 정규화 테이블

| 테이블 | 주요 컬럼 | 목적 |
|---|---|---|
| `brandServices` | `id`, `brandId`, `name`, `priceText`, `durationText`, `detailsJson`, `sortOrder` | 상품·서비스를 여러 개 관리 |
| `brandKnowledge` | `id`, `brandId`, `title`, `content`, `category`, `publishable`, `updatedAt` | 전문 지식과 작업 방식 축적 |
| `brandFaqs` | `id`, `brandId`, `question`, `answer`, `publishable` | 상담 답변 재사용 |
| `brandFacts` | `id`, `brandId`, `statement`, `status`, `sourceId`, `verifiedAt` | 사실 검증 상태 관리 |
| `brandSources` | `id`, `brandId`, `url`, `title`, `sourceType`, `checkedAt`, `allowedForDraft` | 웹·업로드 출처 관리 |
| `onboardingProgress` | `userId`, `brandId`, `step`, `status`, `draftJson`, `updatedAt` | 임시 저장과 중단 후 재개 |

모든 테이블은 `brandId`와 사용자 소유권을 함께 확인해야 합니다. 실제 파일은 데이터베이스에 BLOB으로 넣지 않고 기존 S3 저장 구조를 사용하며, DB에는 파일 URL·키·파일 유형·확인 상태만 저장합니다.

## 7. API 설계

현재 `brands.create`는 기본 정보와 `brief`를 받아 `briefJson`으로 저장합니다. 온보딩을 구현할 때는 한 번에 완료 제출하는 절차와 단계별 저장 절차를 분리하는 것이 좋습니다.

| API | 유형 | 역할 |
|---|---|---|
| `onboarding.start` | mutation | 새 브랜드와 온보딩 세션 생성 |
| `onboarding.saveStep` | mutation | 현재 단계의 임시 입력 저장 |
| `onboarding.get` | query | 중단한 온보딩 복원 |
| `onboarding.complete` | mutation | 필수값 검사 후 브랜드 활성화 |
| `brands.get` | query | 선택 브랜드의 최신 브리프·톤·자료 조회 |
| `brands.update` | mutation | 기존 업체 정보 수정 |
| `brandServices.list/create/update/delete` | query/mutation | 상품·서비스 카드 관리 |
| `brandKnowledge.list/create/update/delete` | query/mutation | 전문 지식 메모 관리 |
| `brandFaqs.list/create/update/delete` | query/mutation | FAQ 관리 |
| `brandSources.list/create/delete` | query/mutation | 공식 출처와 확인일 관리 |
| `content.research` | mutation | 선택된 URL 또는 검색 범위의 자료 수집 |
| `content.generate` | mutation | 서버에서 최신 브리프·톤·허용 출처를 조합해 초안 생성 |

`content.generate`는 최종적으로 클라이언트가 업체 정보를 모두 보내는 방식보다 `brandId`만 신뢰하고 서버에서 브랜드 데이터를 조회하는 방식으로 변경해야 합니다. 이렇게 해야 최신 브리프가 사용되고 다른 브랜드의 정보가 섞이지 않습니다.

## 8. 웹 리서치 모드

인터넷 검색은 기본값으로 켜지 않아야 합니다. 업체 고유 가격·주소·경력·작업 실적은 업체가 제공한 정보가 우선이고, 인터넷 검색은 업종 일반 지식이나 최신 공공 정보 보완에 한정합니다.

생성 전에 사용자는 다음 중 하나를 선택합니다.

| 모드 | 동작 | 비용·위험 |
|---|---|---|
| 업체 정보만 사용 | 저장된 브리프·톤·기존 글로 생성 | 가장 빠르고 통제력이 높음 |
| 지정 링크만 확인 | 사용자가 등록한 공식 URL만 읽음 | 사실 통제가 쉬움 |
| 최신 공개 자료 확인 | 허용된 검색 범위에서 자료 수집 | 시간이 더 걸리고 오래된·상충 정보 검수가 필요 |

검색 결과는 바로 본문에 확정하지 않고 `출처 제목`, `URL`, `확인일`, `사용한 핵심 내용`, `검수 상태`를 함께 저장합니다. 가격·영업시간·의료·안전·법률·효능처럼 민감하거나 변동 가능성이 있는 정보는 `확인 필요` 표시를 유지한 채 초안에 반영하거나 제외합니다.

## 9. 랜딩과 온보딩의 성공 지표

온보딩의 목적은 입력 완료율만 높이는 것이 아니라, 고객이 실제로 첫 초안을 만들고 “내 업체를 이해한 글”이라고 느끼게 하는 것입니다.

| 지표 | 1차 목표 방향 |
|---|---|
| CTA 클릭 후 업체 등록 시작률 | 랜딩 소구점과 온보딩 첫 문구의 일치 여부 확인 |
| 1단계 완료율 | 기본 정보 입력의 부담 측정 |
| 첫 서비스 카드 등록률 | 실제 생성에 필요한 정보 확보 여부 확인 |
| 온보딩 후 첫 초안 생성률 | 등록이 결과로 이어지는지 확인 |
| 첫 초안 수정 후 저장률 | 품질과 편집 UX 확인 |
| 7일 내 브리프 보완률 | 장기적으로 지식 자산이 쌓이는지 확인 |

## 10. 구현 순서

첫 번째 구현에서는 현재 `BrandCreateDialog`를 6단계 화면으로 분리하고, 기존 `brandProfiles.briefJson`에 `services`, `expertise`, `faqs`, `verifiedFacts`, `sourceLinks`를 추가한 하이브리드 JSON 구조로 시작합니다. 이후 실제 사용량과 데이터 크기를 확인한 뒤 반복 데이터부터 정규화 테이블로 옮기는 방식이 안전합니다.

두 번째 단계에서는 `brands.get`과 `brands.update`를 추가하고, `content.generate`가 `brandId`를 기준으로 서버에서 최신 데이터를 조회하게 합니다. 세 번째 단계에서는 제목 3개 추천과 첫 글 생성 결과를 온보딩 완료 화면에 연결합니다. 네 번째 단계에서 URL 분석과 선택적 웹 리서치, 출처 표시를 추가합니다.

> 최종 설계 원칙은 간단합니다. **처음에는 쉽게 시작하게 하고, 업체의 실제 지식은 여러 번에 걸쳐 축적하게 하며, 생성 전에 사용자가 어떤 정보와 출처를 사용했는지 확인할 수 있게 해야 합니다.**
